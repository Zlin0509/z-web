## 接口名称只是开始

工具描述要告诉调用方三件事：它解决什么问题、何时应该使用、使用前需要哪些信息。含糊的名称和宽泛的参数，会把本来能在接口层消除的不确定性推给模型。

比如，把 `update(data)` 拆成 `update_note(note_id, expected_revision, title, body)`，可以显式表达对象、并发约束和可修改字段。

## 用结构表达约束

参数应有类型、取值范围和必要性说明。对于互斥选项，尽量在结构里表达，而不是只写一句「不要同时填写」。

```json
{
  "name": "get_note",
  "description": "按笔记 ID 读取已存在的笔记。",
  "parameters": {
    "type": "object",
    "properties": {
      "note_id": { "type": "string", "minLength": 1 }
    },
    "required": ["note_id"],
    "additionalProperties": false
  }
}
```

接口层仍然需要再次验证。描述和 Schema 有助于生成有效参数，但不能替代服务端授权与输入检查。

## 错误也是接口的一部分

失败结果应该区分「参数错误」「资源不存在」「无权限」「限流」「服务暂不可用」。这些情况对应不同的下一步行动。

```json
{
  "ok": false,
  "error": {
    "code": "REVISION_CONFLICT",
    "message": "笔记已被更新，请重新读取后再提交。",
    "retryable": false
  }
}
```

把所有错误都折叠成 `something went wrong`，会让调用方失去恢复的依据。错误消息还应避免泄漏内部路径、凭证或数据库细节。

## 为重试留下空间

创建资源、发送消息等有副作用的操作，必须考虑「请求成功了，但响应丢了」的情况。使用有明确作用域和过期策略的幂等键，能帮助服务端识别同一次逻辑操作。

> 重试之前，先确认重试语义。读操作的安全性不能直接推广到写操作。

## 一份轻量检查表

- 参数是否能在不猜测的情况下填写？
- 成功结果是否包含后续调用需要的稳定 ID？
- 失败结果是否告诉调用方应该修正、等待还是停止？
- 写操作是否考虑了并发修改和重复执行？
- 返回内容是否被当作数据处理，而非新的系统指令？
